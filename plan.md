# Plan реализации SmartStock AI

## Что сознательно убрано из первоначального ТЗ и переносится на потом

Ниже перечислены функции, которые **не входят в основной план ближайших 2 недель**, потому что они дают мало ценности именно для задачи учета склада, но при этом съедают много времени и сильно повышают риск срыва сроков:

- `FR-27` Голосовой поиск
- сложный `drag-and-drop` для деревьев категорий и локаций
- сложная кастомизация таблиц с сохранением пользовательских layout-профилей
- `LSTM` как отдельная тяжелая ML-ветка
- продвинутое ансамблирование моделей прогноза
- сложные сценарии `What-if`
- `FR-20` Автоподбор аналогов
- `FR-21` сложная детекция аномалий с текстовыми комментариями
- `FR-22` сезонный календарь в полном виде
- `FR-39` интеллектуальная автокатегоризация в полном виде
- рекомендации размещения товара по складу
- маршрутизация сборки в продвинутом виде
- сложное наследование прав и оргструктуры пользователей
- полноценный audit trail абсолютно всех действий во всех сущностях
- `SQLCipher`, если интеграция начнет тормозить основной учетный контур
- автообновление инсталлятора
- сложные PDF-отчеты, если Excel/CSV уже покрывают приемку


## 1. Цель плана

Собрать за 2 недели **почти полный рабочий продукт учета склада**, где главный акцент сделан на:

- номенклатуре;
- остатках;
- приходах;
- расходах;
- инвентаризации;
- локациях;
- поставщиках;
- отчетности;
- импорте и экспорте;
- базовой аналитике дефицита и закупок.

План ниже рассчитан на **2 разработчиков**, которые должны работать параллельно, с минимальными конфликтами в коде.

## 2.2. Что входит в AI/аналитику в первой версии

В первую версию включаем только то, что помогает учету и закупкам:

- сбор истории продаж/расходов;
- прогноз по товарам на основе упрощенного подхода;
- прогноз по категориям;
- рекомендации по закупке;
- fallback-логика для новых товаров;
- визуализация истории и прогноза;
- расчет дефицита и критических позиций.

## 2.3. Что считаем достаточным уровнем реализации

Для дедлайна в 2 недели принимаем такие правила:

- не делаем идеальную enterprise-архитектуру, делаем рабочую;
- критично закрыть учетный контур, а не второстепенные интеллектуальные функции;
- сложные фичи можно реализовать в упрощенном варианте, если пользовательский сценарий уже работает;
- главное: пользователь должен реально вести учет в приложении.

## 4. Простое правило совместной работы

Чтобы 2 разработчика не конфликтовали, используем простой порядок:

1. Все общие сущности фиксируются в `docs/shared-contracts.md`.
2. Если меняется структура общей сущности, сначала меняется `docs/shared-contracts.md`, потом код.
3. Разработчик 1 в основном отвечает за данные, бизнес-логику, хранение и расчеты.
4. Разработчик 2 в основном отвечает за окна, формы, таблицы, навигацию и пользовательские сценарии.
5. На каждом шаге у каждого разработчика своя зона файлов.
6. Внутри шага нельзя одновременно глубоко переделывать одни и те же классы.

## 9. Уточненный AI-план для шага 6

Ниже зафиксированы согласованные решения по внедрению AI/ML на шаге 6. Этот раздел имеет приоритет над более ранними упрощениями в плане, если они противоречат текущим договоренностям.

### 9.1. Что входит в AI-этап обязательно

В шаг 6 обязательно входят:

- автокатегоризация товаров;
- прогноз расхода;
- прогноз по категориям;
- рекомендации по закупке;
- fallback для новых товаров;
- визуализация истории и прогноза;
- автоматическое переобучение по расписанию или вручную;
- базовая аналитика дефицита на основе прогноза.

### 9.2. Что берем в первой реализации на ML.NET

Для первой реализации фиксируем такой стек:

- `ML.NET` как основной ML-стек;
- `SSA` как базовая модель прогноза временных рядов;
- отдельная модель `multiclass text classification` для автокатегоризации по названию товара;
- rule-based слой для закупочных рекомендаций;
- rule-based слой для fallback и части аналитики дефицита.

### 9.3. Что не берем в первую реализацию

В первую реализацию AI не входят:

- `LSTM`;
- сложное ансамблирование моделей;
- продвинутые сценарии `What-if`;
- полноценный подбор аналогов;
- сложная ML-детекция аномалий;
- расширенный сезонный календарь с отдельной моделью.

### 9.4. Зафиксированные решения по данным и прогнозу

Приняты такие решения:

- источник истории для прогноза: только расходные движения;
- возвраты, инвентаризационные корректировки и прочие нецелевые движения должны быть исключены из обучающего ряда;
- базовая гранулярность прогноза: месяц;
- горизонт прогноза: `6`, `9` и `12` месяцев;
- прогноз должен считаться:
  - по каждой товарной позиции;
  - агрегированно по категориям;
- для новых товаров с историей менее `3` месяцев используется fallback по родительской категории;
- общий срок поставки в первой версии задается одним глобальным параметром;
- формула закупки:
  - `Заказ = (Прогноз на срок поставки + Страховой запас) - Остаток - Ожидаемый приход`.

### 9.5. Зафиксированные решения по автокатегоризации

Приняты такие решения:

- автокатегоризация обязательна в шаге 6;
- модель должна предлагать только одну лучшую категорию;
- обучение идет только на уже существующих товарах в базе, у которых категория была назначена вручную;
- основное поле для классификации: наименование товара;
- порог сильной рекомендации: `0.75`;
- если score ниже `0.75`, категория показывается как слабая рекомендация без автоприменения;
- результат автокатегоризации должен возвращать:
  - `CategoryId`;
  - `CategoryName`;
  - score/уверенность модели;
- если уверенность ниже порога, UI должен показывать это как рекомендацию, а не как безусловное назначение.

### 9.6. Минимальный pipeline по прогнозу

Минимальный pipeline прогноза:

1. собрать месячный ряд расхода по товару;
2. отфильтровать выбросы и нецелевые движения;
3. агрегировать значения по месяцам;
4. обучить или обновить `SSA`-модель;
5. посчитать прогноз на `6`, `9`, `12` месяцев;
6. сохранить прогноз и дату расчета в кэш/таблицу результатов;
7. использовать прогноз в расчете закупки и дефицита.

### 9.7. Минимальный pipeline по автокатегоризации

Минимальный pipeline автокатегоризации:

1. собрать обучающий датасет из существующих товаров;
2. взять текст названия товара;
3. нормализовать текст;
4. обучить `ML.NET` multiclass classification pipeline;
5. для нового товара получить одну рекомендуемую категорию и score;
6. показать рекомендацию в карточке товара до сохранения или при вводе названия.

### 9.8. Что должен уметь backend в шаге 6

Backend должен уметь:

- готовить обучающий датасет для прогноза;
- готовить обучающий датасет для автокатегоризации;
- обучать и переобучать модели;
- кэшировать результаты прогноза;
- возвращать прогноз по товару;
- возвращать прогноз по категории;
- возвращать рекомендованный заказ;
- возвращать рекомендацию категории для товара;
- возвращать метаданные модели:
  - дата обучения;
  - объем обучающих данных;
  - score/ошибка модели.

Также фиксируем:

- артефакты моделей `ML.NET` хранятся в файловой системе приложения;
- в базе данных хранятся только метаданные обучения, результаты прогноза и кэш расчетов, если это потребуется;
- автопереобучение запускается на старте приложения.

### 9.9. Что должен уметь UI в шаге 6

UI должен уметь:

- запускать ручное обновление прогноза;
- показывать историю и прогноз на одном графике;
- показывать дату последнего расчета;
- показывать рекомендации по закупке;
- показывать автокатегоризацию в карточке товара;
- позволять пользователю принять или игнорировать рекомендацию категории.

### 9.10. Открытые вопросы перед реализацией

Нужно отдельно утвердить:

- какой объем истории считать минимально достаточным для прогноза по товару;
- как считать страховой запас в первой версии:
  - фиксированное число месяцев;
  - фиксированное число единиц;
  - коэффициент от среднего расхода.

### 9.11. Финально утвержденные параметры первой версии

Для первой версии окончательно зафиксированы такие параметры:

- прогнозная модель: `ML.NET SSA`;
- модель автокатегоризации: `ML.NET multiclass text classification`;
- источник обучающих данных для прогноза: только расходные движения;
- гранулярность прогноза: месяц;
- горизонты прогноза: `6`, `9`, `12` месяцев;
- fallback для новых товаров: если истории меньше `3 месяцев`, использовать родительскую категорию;
- хранение моделей: в файлах;
- автопереобучение: на старте приложения;
- автокатегоризация возвращает одну категорию;
- порог сильной рекомендации категории: `0.75`;
- срок поставки: один глобальный параметр;
- страховой запас: фиксированное число месяцев спроса.

### 9.12. Формула закупки для первой версии

В первой версии формула закупки фиксируется так:

- `ForecastLeadTime = MonthlyForecast * LeadTimeMonths`;
- `SafetyStock = MonthlyForecast * SafetyStockMonths`;
- `RecommendedOrder = (ForecastLeadTime + SafetyStock) - CurrentStock - ExpectedInbound`.

Где:

- `LeadTimeMonths` — глобальный параметр срока поставки;
- `SafetyStockMonths` — глобальный параметр страхового запаса в месяцах спроса.
- можно выполнить инвентаризацию;
- можно импортировать стартовые данные;
- можно выгрузить отчеты;
- есть дашборд по дефициту;
- есть базовая рекомендация по закупке;
- приложение работает локально без интернета;
- критичные сценарии не падают.
