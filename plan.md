# Plan реализации SmartStock AI

## Что сознательно убрано из первоначального ТЗ и переносится на потом

Ниже перечислены функции, которые **не входят в основной план ближайших 2 недель**, потому что они дают мало ценности именно для задачи учета склада, но при этом съедают много времени и сильно повышают риск срыва сроков:

- `FR-27` Голосовой поиск
- сложный `drag-and-drop` для деревьев категорий и локаций
- сложная кастомизация таблиц с сохранением пользовательских layout-профилей
- `LSTM` как отдельная тяжелая ML-ветка
- продвинутое ансамблирование моделей прогноза
- сложные сценарии `What-if`
- `FR-20` Автоподбор аналогов
- `FR-21` сложная детекция аномалий с текстовыми комментариями
- `FR-22` сезонный календарь в полном виде
- `FR-39` интеллектуальная автокатегоризация в полном виде
- рекомендации размещения товара по складу
- маршрутизация сборки в продвинутом виде
- сложное наследование прав и оргструктуры пользователей
- полноценный audit trail абсолютно всех действий во всех сущностях
- `SQLCipher`, если интеграция начнет тормозить основной учетный контур
- автообновление инсталлятора
- сложные PDF-отчеты, если Excel/CSV уже покрывают приемку

Это не удаляется из продукта. Это переносится в **этап 2 после сдачи основной версии**.

## 1. Цель плана

Собрать за 2 недели **почти полный рабочий продукт учета склада**, где главный акцент сделан на:

- номенклатуре;
- остатках;
- приходах;
- расходах;
- инвентаризации;
- локациях;
- поставщиках;
- отчетности;
- импорте и экспорте;
- базовой аналитике дефицита и закупок.

План ниже рассчитан на **2 разработчиков**, которые должны работать параллельно, с минимальными конфликтами в коде.

## 2. Что должно войти в основную версию

## 2.1. Обязательный функционал

- карточка товара
- категории товаров
- пользовательские атрибуты категорий в упрощенном виде
- изображения товаров
- поставщики
- локации хранения
- приходные накладные
- расходные накладные
- резервирование
- списание
- инвентаризация
- акты расхождений
- учет остатков
- история движений товара
- базовый аудит ключевых операций
- базовые пользователи и роли
- дашборд
- поиск и фильтры
- стандартные отчеты
- импорт Excel/CSV
- экспорт Excel/CSV/PDF
- backup/restore
- локальная работа без интернета

## 2.2. Что входит в AI/аналитику в первой версии

В первую версию включаем только то, что помогает учету и закупкам:

- сбор истории продаж/расходов;
- прогноз по товарам на основе упрощенного подхода;
- прогноз по категориям;
- рекомендации по закупке;
- fallback-логика для новых товаров;
- визуализация истории и прогноза;
- расчет дефицита и критических позиций.

## 2.3. Что считаем достаточным уровнем реализации

Для дедлайна в 2 недели принимаем такие правила:

- не делаем идеальную enterprise-архитектуру, делаем рабочую;
- критично закрыть учетный контур, а не второстепенные интеллектуальные функции;
- сложные фичи можно реализовать в упрощенном варианте, если пользовательский сценарий уже работает;
- главное: пользователь должен реально вести учет в приложении.

## 3. Рекомендуемая структура проекта

Чтобы команда не утонула в новом стеке, структура должна быть простой:

```text
SmartStockAI.sln
src/
  SmartStockAI.App
  SmartStockAI.Core
  SmartStockAI.Data
  SmartStockAI.Reporting
tests/
  SmartStockAI.Tests
docs/
  shared-contracts.md
  fr-traceability.md
```

## 4. Простое правило совместной работы

Чтобы 2 разработчика не конфликтовали, используем простой порядок:

1. Все общие сущности фиксируются в `docs/shared-contracts.md`.
2. Если меняется структура общей сущности, сначала меняется `docs/shared-contracts.md`, потом код.
3. Разработчик 1 в основном отвечает за данные, бизнес-логику, хранение и расчеты.
4. Разработчик 2 в основном отвечает за окна, формы, таблицы, навигацию и пользовательские сценарии.
5. На каждом шаге у каждого разработчика своя зона файлов.
6. Внутри шага нельзя одновременно глубоко переделывать одни и те же классы.

## 6. Шаги реализации

Ниже план разбит на шаги. Каждый шаг рассчитан примерно на `2-3 дня`, кроме финального шага стабилизации.

## Шаг 1. Стартовый каркас и база данных

### Оценка

`2 дня`

### Цель

Собрать запускаемое desktop-приложение с локальной БД и базовой навигацией.

### Что должно быть готово по итогам шага

- solution и проекты;
- WPF shell;
- базовая навигация;
- подключенная SQLite база;
- первая миграция;
- базовые сущности;
- общая структура каталогов;
- документ `docs/shared-contracts.md`.

### Разработчик 1

- создает solution;
- поднимает `SQLite + EF Core`;
- создает базовые сущности:
  - `Product`
  - `Category`
  - `Supplier`
  - `Location`
  - `User`
  - `StockMovement`
- настраивает первую миграцию;
- заводит базовый контекст БД;
- создает `docs/shared-contracts.md` с обязательными полями сущностей.

### Разработчик 2

- создает WPF shell;
- делает главное окно;
- делает боковую навигацию;
- добавляет пустые страницы:
  - товары
  - категории
  - поставщики
  - локации
  - приход
  - расход
  - инвентаризация
  - отчеты
  - дашборд;
- подготавливает общие стили и базовые таблицы.

### Точка синхронизации

- согласовать названия сущностей и обязательные поля;
- договориться, какие поля точно используются в UI уже на следующем шаге.

## Шаг 3. Приход, расход, остатки, резервирование

### Оценка

`2-3 дня`

### Цель

Собрать основной учетный контур движения товара.

### Что должно быть готово по итогам шага

- приходные накладные;
- расходные накладные;
- пересчет остатков;
- история движений;
- резервирование;
- базовое списание;
- проверка нехватки товара.

### Разработчик 1

- реализует модели документов прихода и расхода;
- реализует строки документов;
- реализует проведение прихода;
- реализует проведение расхода;
- реализует резервирование под заказ;
- реализует обновление остатков;
- реализует журнал движений;
- добавляет базовую логику списания;
- если успевает, добавляет FIFO как отдельный режим; если нет, оставляет упрощенное списание с правильным учетом остатков.

### Разработчик 2

- делает экран приходной накладной;
- делает экран расходной накладной;
- делает добавление строк товара в документ;
- делает список документов;
- показывает ошибки нехватки остатка;
- показывает текущий остаток рядом с товаром;
- делает экран просмотра истории движений товара.

### Точка синхронизации

- финально согласовать жизненный цикл документа:
  - черновик
  - проведение
  - отмена при необходимости;
- зафиксировать, какие поля движения UI обязан показать.

## 8. Definition of Done для основной версии

Основная версия считается готовой, если:

- можно создать и редактировать товар;
- можно назначить товару категорию, поставщика и локацию;
- можно провести приход;
- можно провести расход;
- остатки считаются корректно;
- можно выполнить инвентаризацию;
- можно импортировать стартовые данные;
- можно выгрузить отчеты;
- есть дашборд по дефициту;
- есть базовая рекомендация по закупке;
- приложение работает локально без интернета;
- критичные сценарии не падают.
